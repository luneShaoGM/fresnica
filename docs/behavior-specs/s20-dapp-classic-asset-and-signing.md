# S18 / S20: Reviewed Classic dApp asset and signing requests

Phase 2b, candidate. Clean-room Adapt of Stellar's Freighter request-to-review behavior. Owner: dApps, existing transaction and trustline capabilities, and platform WebView/SDK. This is a Classic slice, not complete S20 parity.

- `SUBMIT_TOKEN` with an issued Classic code and issuer can prepare an Add Trustline only for the connected, current selected Classic account and network. Display the verified origin, network, full issuer, exact fee/limit and reserve impact. Ignore dApp-supplied presentation metadata and URLs. A supplied response ID must equal the canonical code/issuer or its network-derived Stellar Asset Contract address. Use the existing exact-XDR trustline review, reserve and ledger authorization/revalidation, fresh App Passphrase, pending-submission registration/recovery, and normal wallet broadcast; return success only on known submission. No new signing or broadcast pathway.
- `SUBMIT_TRANSACTION` still returns the signed envelope to the original page rather than broadcasting. In addition to the existing bounded plain payments, support a single account-creation operation or a single positive-limit issued-asset ChangeTrust. Display the exact intent; reject multi-op combinations involving the new operations, removals, pool shares, fee bumps and unreviewed preconditions. The separate [Soroban Testnet review](s20-dapp-soroban-transaction-signing.md) defines supported contract invocations. Every signature requires fresh App Passphrase. A dApp connection is not approval.
- Transaction/asset success requires the original native document's one-use reply path. Never inject signature or asset completion into the current document. Cross-origin navigation, document replacement, toolbar navigation, account/network changes and expiry retire the review. The scoped one-use native reply has a bounded 16 KiB transport limit. Android needs a supported, guarded in-app WebView; the external-browser fallback is not equivalent.
- `SUBMIT_AUTH_ENTRY` and contract-token addition remain unsupported. The pinned SDK's Rust Core contains native Soroban auth-entry signing logic, but the published native binding and both pinned RN adapters do not expose a protected-signer operation for it. Future work uses an explicit native contract and Rust conformance vectors, not SEP-53 or a generic signature. Bind the exact auth-entry/preimage, network, signer, contract/function/arguments and nested invocation scope, nonce and expiry; reject unreviewable intents, test on Testnet first. Contract-token tracking also needs the independently scoped S06/S10 product path. WalletConnect stays off.

Before mainnet readiness, run independent exact-HEAD review and Android/iOS native tests: request approval/decline; stale account, network, origin, reload, navigation and expiry; exact original reply behavior; valid and wrong passphrase; no automatic funding/broadcast outside explicit trustline approval. Use a disposable Testnet wallet, do not use a production account for acceptance.
