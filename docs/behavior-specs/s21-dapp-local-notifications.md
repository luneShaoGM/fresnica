# S21 Android dApp local notifications

Phase 2b shell is available. S21 is an Adapt slice in the existing strict dApps/navigation scopes. Reference behavior: Stellar at bd0f4540b2496a57314e4e29bc6fcf8ff691b60f. This is a clean-room implementation. The capability validates and authorizes; the browser manages document lifetime; Android owns system notification delivery.

Only a verified, live top-level HTTPS document with explicit connection consent for the active origin, account and network can request a notification. Connection consent only makes a request eligible. The browser names the verified website and requires a separate user decision for each notification. Consent is consumed once and never saved. The notification request must carry `expiresAt`, an integer Unix timestamp in milliseconds fixed by the client before sending. The client uses that same deadline to end its wait (including any custom shorter timeout); bridge transit never restarts the window. The wallet accepts only an unexpired deadline at most five seconds away, schedules approval expiry for the remaining time, and checks both the shared wall-clock expiry and a monotonic remaining-time deadline even if the timer callback has not run. Android rechecks the shared expiry immediately before posting. Missing, invalid, expired or overlong deadlines fail closed without offering approval. The old five-field client envelope is deliberately unsupported for delivery: clients must upgrade to include their actual deadline, rather than receiving a fresh wallet-side lease. Browser Back, Forward and Reload cancel the approval at the moment the action starts. Catalog display trust does not suffice. The bridge accepts Stellar's SHOW_SYSTEM_NOTIFICATION envelope with bounded nonblank title and body, and rejects duplicate IDs. It replies with the matching ID and shown flag only while the original document is live.

On Android the owner can enable notifications in system App Info. A dApp cannot open the Android permission prompt. The browser rechecks the live document, account, network and unconsumed consent immediately before a synchronous native call. Android checks the resumed foreground activity before posting and does not enqueue a later UI-thread delivery. Denied or disabled permissions, lack of foreground window focus, or delivery failures return shown=false. Notifications attribute the verified origin, hide content on the lock screen, replace the prior dApp notification, and can update at most once per ten seconds. iOS returns shown=false, matching the Android-only delivery scope. No push backend, URL tap routing, or signing permission is involved.

Acceptance on physical Android: enable/disable notifications at system level, connect and revoke a dApp, post via a live main-frame session, confirm origin and lock-screen privacy, then repeat after navigation, background or an account/network switch. Record native product acceptance separately from repository tests.

## Shared expiry contract

Before posting `SHOW_SYSTEM_NOTIFICATION`, the client fixes `expiresAt = Date.now() + timeoutMs`, where `0 < timeoutMs <= 5000`, includes it as the sixth envelope field, and ends its wait at that timestamp. It must not abandon the request earlier and report a definitive `shown=false`. Responses preserve the existing source, matching `messagedId` and boolean `shown`. A response that does not arrive before the deadline means no timely delivery confirmation; transport failure is not proof that Android never posted before the deadline.

Repository regression cases cover an already expired request after bridge transit, a request arriving with only part of its budget remaining, a shorter client budget, expiry with a delayed wallet timer, and a backward wall-clock adjustment. These are automated timing models, not native bridge/device acceptance. The companion [Stellar PR #23](https://github.com/luneShaoGM/Stellar/pull/23) Demo revision `5a6ffb08040d0c9c2f5a99839323da1120c792fa` sends and waits on the same `expiresAt`, rejects invalid/overlong budgets and refuses late success responses. The Mobile CI fetches that exact external commit outside the target source tree and runs its real sender through the injected bridge, browser approval and delivery port. Six automated linked cases cover approval, expired-in-transit requests, remaining-budget expiry, a short client budget, cancellation and navigation. The native delivery port is mocked; no Android device acceptance is claimed. The old pinned donor snapshot and provenance index remain unchanged. Deploying the compatible Demo revision remains a release prerequisite; a companion PR alone does not change the live website.

To reproduce the linked repository test, set `FRESNICA_DEMO_NOTIFICATION_MODULE` to the absolute path of `demo-dapp/src/wallet/notification.ts` in the companion checkout, then run `npm test -- --watchman=false --runTestsByPath src/features/dapps/screens/DappBrowserScreen/__tests__/DappBrowserScreen.test.ts`. Without that external checkout the six integration cases are explicitly skipped; CI supplies the fixed revision and executes them.
