# S21 Android dApp local notifications

Phase 2b shell is available. S21 is an Adapt slice in the existing strict dApps/navigation scopes. Reference behavior: Stellar at bd0f4540b2496a57314e4e29bc6fcf8ff691b60f. This is a clean-room implementation. The capability validates and authorizes; the browser manages document lifetime; Android owns system notification delivery.

Only a verified, live top-level HTTPS document with explicit connection consent for the active origin, account and network can request a notification. Connection consent only makes a request eligible. The browser names the verified website and requires a separate user decision for each notification. Consent is consumed once and never saved. The notification request must carry `clock: "android-elapsed-realtime"` and `expiresAt`, an integer Android `SystemClock.elapsedRealtime()` timestamp in milliseconds, fixed by the client before sending. The injected `window.stellar.notificationNow()` and the wallet's synchronous clock port both read this same native clock; Android delivery checks it directly. No wall-clock timestamp or independently rebased JavaScript clock is accepted as a substitute. The client and wallet consume the same original budget even if the wall clock moves while a request is in transit. The wallet accepts only an unexpired deadline at most five seconds away and checks it again on approval. Missing clock access, invalid/expired/overlong deadlines fail closed. Requests missing the explicit clock tag, including old five-field and six-field wall-clock-only requests, cannot deliver. Browser Back, Forward and Reload cancel the approval at the moment the action starts. Catalog display trust does not suffice. The bridge accepts Stellar's SHOW_SYSTEM_NOTIFICATION envelope with bounded nonblank title and body, and rejects duplicate IDs. It replies with the matching ID and shown flag only while the original document is live.

On Android the owner can enable notifications in system App Info. A dApp cannot open the Android permission prompt. The browser rechecks the live document, account, network and unconsumed consent immediately before a synchronous native call. Android checks the resumed foreground activity before posting and does not enqueue a later UI-thread delivery. Denied or disabled permissions, lack of foreground window focus, or delivery failures return shown=false. Notifications attribute the verified origin, hide content on the lock screen, replace the prior dApp notification, and can update at most once per ten seconds. iOS returns shown=false, matching the Android-only delivery scope. No push backend, URL tap routing, or signing permission is involved.

Acceptance on physical Android: enable/disable notifications at system level, connect and revoke a dApp, post via a live main-frame session, confirm origin and lock-screen privacy, then repeat after navigation, background or an account/network switch. Record native product acceptance separately from repository tests.

## Shared expiry contract

Before posting `SHOW_SYSTEM_NOTIFICATION`, the client reads the injected native clock and fixes `expiresAt = window.stellar.notificationNow() + timeoutMs`, where `0 < timeoutMs <= 5000`. Its timer is only a wake-up mechanism: completion and success-response checks use that same native clock. Timer callbacks that fire before the shared deadline re-arm for the remaining budget; missing, invalid or throwing clock reads before sending reject without posting. Date/time changes cannot extend or prematurely end this lifetime. Wallet timers similarly consume `expiresAt - nativeNow()` without rebasing the deadline at receipt. Android checks `SystemClock.elapsedRealtime() < expiresAt` directly immediately before posting. Responses preserve the existing source, matching `messagedId` and boolean `shown`. A response that does not arrive before the deadline means no timely delivery confirmation; transport failure is not proof that Android never posted before the deadline.

The WebView patch exposes only a read-only monotonic-time method, including in frames. It has no permission, account or notification methods. Notification messages still require the existing verified top-level HTTPS WebMessageListener; its insecure message fallback stays disabled. iOS has no notification clock or delivery support. The read port and new protocol must be reviewed together with the companion Demo upgrade.

Repository regression cases cover an already expired request after bridge transit, a request arriving with only part of its budget remaining, a shorter client budget, expiry with a delayed wallet timer, and a backward wall-clock adjustment. These are automated timing models, not native bridge/device acceptance. The companion [Stellar PR #23](https://github.com/luneShaoGM/Stellar/pull/23) Demo revision `4e13c7c63a60c531713e3311680da029dda7412f` sends and waits on the same `expiresAt`, rejects invalid/overlong budgets and refuses late success responses. Local linked verification loads that exact external commit outside the target source tree and runs its real sender through the injected bridge, browser approval and delivery port. Each repository runs its own CI; Mobile CI has no permission to read the separate Stellar repository, so it does not fetch the client or claim linked execution. Ten automated linked cases cover approval, expired-in-transit requests, remaining-budget expiry, a short client budget, cancellation, navigation and in-transit wall-clock rollback (including already expired receipt, timely approval and forward-then-backward correction). The native delivery port is mocked; no Android device acceptance is claimed. The old pinned donor snapshot and provenance index remain unchanged. Deploying the compatible Demo revision remains a release prerequisite; a companion PR alone does not change the live website.

To reproduce the linked repository test, set `FRESNICA_DEMO_NOTIFICATION_MODULE` to the absolute path of `demo-dapp/src/wallet/notification.ts` in the companion checkout, then run `npm test -- --watchman=false --runTestsByPath src/features/dapps/screens/DappBrowserScreen/__tests__/DappBrowserScreen.test.ts`. ## Native clock mechanism check

On emulator-5554, `DappNotificationClockTest` passed: a real Android WebView calls the production read-only JavascriptInterface clock class, and both sampled values fall between reads from the production wallet module's clock method. This checks the native time domain and JavascriptInterface conversion, not the full React Native bridge, origin/authentication path, OS clock changes, or notification posting. Wall-clock correction during transit is covered by the linked automated timing model. Physical-device and native notification product acceptance remain NOT RUN.

Rebuild with `./gradlew :app:assembleDebug :app:assembleDebugAndroidTest -PreactNativeArchitectures=arm64-v8a -PfresnicaTestInstrumentationRunner=com.fresnica.wallet.DappNotificationClockTest`, install both debug APKs, then run `adb shell am instrument -w -r com.fresnica.wallet.test.test/com.fresnica.wallet.DappNotificationClockTest`. Require `INSTRUMENTATION_RESULT: success=true`; a zero shell exit alone is not evidence of a pass. The default instrumentation runner remains the existing browser/network test.
