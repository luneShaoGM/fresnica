## LC1 Lifecycle refresh and display read lifetime

LC1 is merged in PR #111. Its user-visible outcome is automatic revalidation on foreground/network recovery even when there are no pending local transactions.

1. On active startup, refresh revisions for visible accounts on the configured network and independently reconcile pending transactions. Hidden and other-network accounts are excluded. Revision changes themselves never fetch every account; focused screens read their current account.
2. Returning to active from any non-active state refreshes the current inventory independently of pending outcomes. Repeated active callbacks do not retrigger. Inactive pauses display reads but does not cancel or authorize a signing/submission operation and does not imply an application lock.
3. Connectivity is online, offline or unknown. Initial unknown permits reads through the existing gateway. The first definitive online event can retry an initial failure without requiring an earlier offline event. Once offline is known, unknown does not silently promote it to online.
4. Definite offline marks current-network public reads stale, stops dispatching new display requests and prevents pending reconciliation from starting through this lifecycle entry point. Returning online refreshes and reconciles only when foreground. A background recovery is remembered and applied on foreground return.
5. Home, Asset Details, Activity and Operation Details load automatically only when both focused and foreground. Activity may hydrate cached content while foreground but offline; an offline read failure retains its existing degraded-cache behavior. LC1 does not add a Balance cache.
6. Concurrent identical display reads share an in-flight request for the same parameters and account revision. Completed results are not cached by the request gate. A failure can be retried. A new invalidation requires a new request rather than reusing the older revision.
7. Background/foreground and connectivity changes replace the runtime generation. Display results from older generations or older account revisions are rejected before presentation/cache consumption, including active → background → active transitions. Requests queued before a generation change must not start afterward.
8. List coalescing includes address, cursor and limit. Operation lookups require the requesting account address and include it with the operation ID in their coalescing key. They use that account revision for both request sharing and stale-result rejection; account-association validation remains in History. There is one configured network/gateway per service container; LC4 defines endpoint generations for public reads; write/preparation endpoint changes still require a new configured container.
9. Unsubscribe is idempotent and ignores late native callbacks. Disposal pauses new display reads. An underlying request may still finish because cancellation is not exposed by existing gateway ports; its obsolete success must not be accepted. Existing in-flight transaction recovery shutdown semantics are not changed by LC1.
10. Lifecycle refresh failures are diagnosed separately from transaction results. A reconciliation failure must not prevent the independent public read invalidation. No synthetic transaction hash is created for lifecycle refresh.

LC1 changes no database schema, cached ledger authority, signer material, transaction retry or navigation destination. Existing transaction invalidation callers remain compatible. No new dependency is needed.

## LC2 Balance display cache contract

LC1 was merged in PR #111 as `245262327fba37123a7c91befcb1902d4ab4a8ea` after independent approval of `88f6ee5`. LC2 is a separate cache/migration slice. It adds no ledger-write semantics and preserves the original live Balance loader for transaction preparation.

One replaceable snapshot per network/classic account address stores normalized active or inactive Balance DTOs, schema version and last successful read time. Unsupported contract accounts are not persisted. Cache reads and writes are best effort; a successful live result remains usable if persistence fails. Invalid shape/version/address clears only that cache partition. Balances remain exact decimal strings. Cached fields cannot contain signer, envelope, XDR, pending-submission or raw Horizon data. Snapshot size is bounded; account deletion removes its partition. Realm migration adds a top-level entity and preserves all existing wallet and recovery entities.

Home and Asset Details restore matching snapshots, mark them stale, then reread through LC1's display gate. Refresh failures preserve the last successful snapshot and timestamp, and expose Retry. No matching snapshot means a full error state. Live inactive results replace older active data; no speculative arithmetic is performed. Foreground, focus, transaction invalidation and manual refresh mark displayed values stale until successful revalidation. Cached/stale availability does not enable Send/Swap/Manage Assets or Friendbot; their own existing capabilities still validate live state.

An account/identity/network change cannot display or write another partition's data. Refresh completion is accepted only for the current request lifetime; no cache write occurs from a disposed screen or superseded request. Neither expiry nor failure deletes the only usable offline snapshot. Balance caches remain display-only and are never injected into Send, Swap quote/preflight, signing or submission.

Acceptance includes memory/Realm contract parity, corrupt/version/address/size/decimal validation, v5→v6 preservation and close/reopen, deletion/failure guards, cached loading→successful refresh and cached loading→failure→retry, inactive replacement, cross-account isolation, cache-write failure and lifecycle cancellation. Real device offline/restart acceptance remains separately recorded.

## LC3 selected-account foreground synchronization contract

Trace: S05-LC3 / S13-LC3; Phase 0 passed, reuse Phase 2a/2b. Adopt selected-account event awareness, fallback and recovery / Adapt to App-owned committed selection and read invalidation / Exclude global services, event arithmetic, cached authorization, all-account notifications and background push. The implementation is independently written; no reference source or assets are migrated. Existing strict App readModels/navigation scopes cover the composition and lifecycle owner. Capability exposes only the public Effects port; Platform implements one connection and REST checkpoint, without retry policy. No schema/dependency/native build setting is changed.

1. MainTabs binds the existing committed selection store to one App-owned sync scope, independent of the focused Tab. This includes synchronous A→B→A commits, inventory changes, hiding/deletion, and scope disposal. Only a visible, current-network classic account is eligible. Background or definitive offline stops connections, probes and timers. Foreground/online starts a fresh session; old callbacks and pending checkpoints cannot affect it. Service close stops sync before Realm closes. Display reads remain subject to LC1 focus/foreground rules; another Tab retains dirty revisions until its next focused read.
2. Platform opens `/accounts/{address}/effects?cursor=now&order=asc` as SSE. On reconnect within the same scope it uses the last accepted opaque `paging_token`; it never converts tokens to numbers, persists cursors or claims complete History recovery. A rejected cursor (HTTP 400/410) resets to `now` and handshake revalidation covers current state. Runtime/selection/container changes discard cursor and dedup state.
3. The React Native transport uses incremental XMLHttpRequest progress, avoiding Node EventSource/fetch-stream dependencies. It accepts HTTP 200 `text/event-stream`, parses LF/CR/CRLF, chunk boundaries, BOM, comments and multiline data, and projects only bounded public paging tokens. Malformed events, EOF/errors, wrong MIME and oversized input close the connection. Individual events are bounded to 32 KiB, cumulative XHR response to 512 KiB (then reconnect), and dedup to 512 tokens. The adapter does not reconnect itself.
4. Successful connection establishment triggers selected-account invalidation and a REST checkpoint after the stream cursor is established, closing the initial/reconnect gap. Events only mark a dirty revision; Balance and History page-one continue their existing authoritative reads. A fixed 250 ms batch coalesces effect bursts. Additional events while current-generation/current-revision display reads are pending retain one dirty follow-up rather than repeatedly superseding slow requests. The follow-up dispatches when reads settle; its 30-second maximum wait starts when this dirty batch is first queued and is not extended by additional events. This prevents a stuck read from blocking invalidation forever. LC1 manual/lifecycle revision rejection and transaction invalidation remain unchanged. LC4 still owns broader node timeouts/backpressure.
5. Stream handshake timeout is 10 seconds. Stream failure switches the root-tab status to a localized polling notice and starts one App-owned reconnect timer: 2-second exponential base, capped at 60 seconds, with 75–100% jitter. Duplicate failure callbacks cannot create duplicate retries. Fresh effects reset backoff; replay alone does not. Timers and callbacks are session/version guarded, including synchronous adapter setup failure.
6. REST `/effects?order=desc&limit=1` checks every 15 seconds in fallback and every 30 seconds while live. Each probe has an 8-second timeout and abort signal, at most one logical in-flight probe and one queued handshake check. A changed checkpoint absent from the stream exposes silent delivery loss and forces recovery; already delivered tokens do not cause false recovery when REST lags. A checkpoint started before a newer connection cannot tear that connection down. Successful checkpoints also revalidate unchanged data, allowing an earlier failed/delayed display read to recover. A missing account (404) remains eligible for first-funding recovery. Other failures retain polling rather than manufacturing balances or submitting transactions.
7. This one configured network/container owns the endpoint lifetime. Dynamic node changes, cross-node network verification, post-submit bounded convergence and node-wide rate-limit policy remain LC4. Continuous foreground UI receipt is not accepted until Android and iOS native flows and the proposed five-second queryable-to-display target are measured. Root-tab fallback notice does not promote a display snapshot to live transaction authority.

Protocol inputs: [Stellar account Effects streaming](https://developers.stellar.org/docs/data/apis/horizon/api-reference/get-effects-by-account-id) documents `cursor=now`; [SSE event framing](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) defines event-stream text framing. These protocol references do not prove React Native device delivery.

## LC4 node read recovery and post-submit convergence contract

Trace: S05-LC4 / S13-LC4. Phase 0 passed; reuse Phase 2a/2b. Adopt node health, cooldown and bounded read convergence / Adapt to App-owned read session and the existing transaction recovery coordinator / Exclude global services, automatic resubmission, cached authorization and new node-selection UI. Implementation is independently written; no donor source/assets, schema, native configuration or dependency changes. The existing strict App read-model and navigation scopes cover this slice. Capability exposes typed safe node failures; Platform owns abortable public HTTP and wire normalization; App owns retry/lifecycle policy.

1. Device connectivity and Horizon health are distinct. Foreground + non-offline permits an HTTPS root probe; only the configured network passphrase opens reads. The public session has checking, healthy, cooldown, wrong-network, paused and closed states. Root 404/malformed/failed responses cannot leave it checking forever. Wrong-network responses never open reads.
2. Lifecycle pending reconciliation waits for node health and runs again on every healthy generation, so startup verification or cooldown cannot consume its only recovery trigger. It reuses the existing coordinator for the whole unresolved queue, independently of the 16-job display follow-up bound. Public Balance, History, operation detail, Effects checkpoints and hash-bound transaction outcome queries share the node session. Each request has a 10-second logical deadline and AbortSignal. Runtime changes, endpoint replacement and close replace its generation; late responses are rejected even if the transport ignores abort. Existing account revision gates still apply above it. No endpoint appears in diagnostics: only safe phase, generation and failure enums.
3. Timeout, transport, 429, 5xx, protocol and wrong-network failures close the current generation. One App retry owner uses exponential 2–60 second backoff with 75–100% jitter. A successful root alone does not reset repeated business-read failures; a successful business read after 30 healthy seconds does. Valid `Retry-After` delta-seconds or HTTP-date sets a minimum cooldown, including values longer than the exponential cap and background/resume. Manual retry cannot bypass this deadline. Account/operation 404 and transaction-unknown 404 retain their existing semantics; ordinary request 4xx are not global retry loops.
4. Shared node cooldown pauses Effects streams, polling and reconnect timers; a healthy generation restarts them. Stream-only EOF/parser/transport faults retain LC3 polling/reconnect when REST remains healthy; explicit stream 429/5xx reports safe metadata to the shared owner. No second Effects checkpoint timeout competes with the shared production deadline.
5. `replaceEndpoint` is an internal public-read session API: it aborts old reads and checks the new endpoint's network before restarting. This slice adds no Settings picker. Preparation, authorization, signing and broadcast retain the original configured SDK endpoint and transaction pipeline. Changing that endpoint still requires rebuilding the configured service container. Public endpoint generation must never silently change a reviewed transaction.
6. A local transaction invalidation starts at most one network/account/hash follow-up job, only for a matching pending submission and visible classic account. Ordinary refresh does not start jobs. At most 16 jobs are active, with a bounded 256-key seen set. Each job has an absolute 60-second lifetime and up to five attempts after 1/2/4/8/16-second delays; duplicate notifications, reconnects and background time never extend its budget. Paused jobs do not dispatch reads and expire on the next wake or disposal.
7. Submitting/uncertain records are reconciled through the existing hash-bound transaction recovery coordinator. This owner cannot sign, submit or resubmit. Rejected outcomes stop following. Unknown outcomes keep the existing pending-intent block. Balance and History reads run concurrently; obsolete runtime, endpoint, account identity or revision results cannot populate caches. Best-effort cache writes retain the established display-only authority boundary.
8. Convergence requires coordinator confirmation, the matching hash in History page one, and an account `last_modified_ledger` at least the confirmed transaction ledger (or matching history plus inactive account after account merge). Missing history/ledger evidence exhausts the bounded job rather than claiming success. This public ledger number is not a new persisted authorization source. Other updates can make page one omit a busy account's transaction; the safe outcome is bounded exhaustion with ordinary LC3 synchronization continuing.
9. Root-tab feedback distinguishes verification, wrong network, rate limit and unavailable reads, with retry that respects cooldown. Existing cache freshness remains visible on the owning screens. Close disposes convergence, foreground sync, node requests/timers/subscriptions, then persistence; partial service construction also cleans up acquired owners.

Protocol references: [Horizon rate limiting](https://developers.stellar.org/docs/data/apis/horizon/api-reference/structure/rate-limiting) and [Retry-After wire forms](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After). These inform HTTP handling, not transaction confirmation authority.
