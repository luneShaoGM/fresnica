# S14 / S16 / S17 dApp catalog and browser controls

Phase F4, scoped improvement to existing implemented dApps surfaces; native acceptance remains incomplete. Decision: **Adapt** Stellar's dApp discovery, browsing and connection-management behavior without donor source. Fresnica owners: dApps screens, existing catalog and dApp interaction capability ports, app composition for system sharing. No new native bridge method, storage schema, signing permission, or ledger write.

- **S14:** With the dedicated directory visible, focused and online, pull-to-refresh uses the existing source and cache policy and keeps search/category and last successful content if refresh fails. Recommended candidates are shown in the API's featured order only when their ID and URL match a visible catalog listing. The complete catalog remains available. No popularity is inferred from the featured list. Recent may display a unique known catalog title plus the canonical origin, but its launch stays on the custom website confirmation path. Ambiguous or unknown origins remain plain origins.
- **S16 / S17:** Browser connection details show the current website and network; the public connected account is shown only for a live read connection. Share or select/copy the website origin, not a full path, query or fragment, and never pass wallet details to the share sheet. Disconnect closes the embedded page and immediately retires the WebView session and pending replies; revoke only the matching saved origin/account/network grant, if present. Storage failure stops the current session and is reported rather than claiming durable revocation. Reload, navigation, and wallet account/network changes keep existing document boundaries. Directory read access is not signing consent; signing remains separately reviewed and requires fresh App Passphrase.
- **Acceptance:** On Android and iOS, use a nonfunded fixture and verify catalog refresh success/failure, origin-only Recent and sharing, touch/screen-reader access to the connection controls, exact durable grant removal after reopen, and stale callback suppression. No live transaction is part of this slice.
- **Not implemented here:** Soroban token addition needs the shared wallet-visible account/network scoped token registry; Soroban authorization signing needs a reviewed narrow protected SDK/native interface and independent operation review. No ordinary message signature substitution. A distinct Popular group is not exposed because the current directory contract has no independent popularity field. WalletConnect stays off.
