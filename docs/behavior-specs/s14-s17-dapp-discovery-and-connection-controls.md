# S14 / S16 / S17 dApp catalog and browser controls

Phase F4, scoped improvement to existing implemented dApps surfaces; native acceptance remains incomplete. Decision: **Adapt** Stellar's dApp discovery, browsing and connection-management behavior without donor source. Fresnica owners: dApps screens, existing catalog and dApp interaction capability ports, app composition for system sharing. No new native bridge method, storage schema, signing permission, or ledger write.

- **S14:** With the dedicated directory visible, focused and online, pull-to-refresh uses the existing source and cache policy and keeps search/category and last successful content if refresh fails. Recommended candidates are shown in the API's featured order only when their ID and URL match a visible catalog listing. The complete catalog remains available. No popularity is inferred from the featured list. Recent may display a unique known catalog title plus the canonical origin, but its launch stays on the custom website confirmation path. Ambiguous or unknown origins remain plain origins.
- **S16 / S17:** Browser connection details show the current website and network; the public connected account is shown only for a live read connection. Share or select/copy the website origin, not a full path, query or fragment, and never pass wallet details to the share sheet. Disconnect closes the embedded page and immediately retires the WebView session and pending replies; revoke only the matching saved origin/account/network grant, if present. Storage failure stops the current session and is reported rather than claiming durable revocation. Reload, navigation, and wallet account/network changes keep existing document boundaries. Directory read access is not signing consent; signing remains separately reviewed and requires fresh App Passphrase.
- **Acceptance:** On Android and iOS, use a nonfunded fixture and verify catalog refresh success/failure, origin-only Recent and sharing, touch/screen-reader access to the connection controls, exact durable grant removal after reopen, and stale callback suppression. No live transaction is part of this slice.
- **Not implemented here:** Soroban authorization signing needs a reviewed narrow protected SDK/native interface and independent operation review. No ordinary message signature substitution. A distinct Popular group is not exposed because the current directory contract has no independent popularity field. WalletConnect stays off.

## 2026-11-27 follow-up in the same draft

- Account choice uses the wallet's current-network visible Classic account list and normal persisted selection. It synchronously closes the old WebView and opens a new instance at the public origin. The reopened instance does not inherit the catalog proof or even a saved grant for the new account; the first request must obtain consent. Network choice uses the existing network settings sheet and its developer-mode/node policy. The old browser session closes before the picker opens, even if the picker is canceled. Reopen the site from the new network's dApp list.
- Soroban contract-only `SUBMIT_TOKEN` requests get a wallet-owned confirmation with origin, network, account, exact checksum-validated contract ID, and RPC disclosure. No token data is sent to RPC before confirmation. Read-only SEP-41 simulation validates metadata and writes a network/account-scoped local registry record only if the native document, request, account, and deadline are still current. The wallet displays tracked tokens separately from Classic balances, with unknown balance distinct from zero. No signing or transaction submission, no page metadata trusted, no signed response to an expired document, and no fallback to a Classic trustline. Soroban authorization signing remains out of scope.

## Directory directly opens the browser (Stellar flow alignment)

Tapping a catalog row enters the embedded browser directly without loading or requiring a separate details sheet. The live catalog itself supplies the exact launch URL; the existing launch proof and first native verified document still bind automatic public-address access. A stale list can display or open rows where browseable but cannot issue that proof. The catalog identity is a display-only one-use route handoff, never a permission; a foreign origin does not inherit it. Unsupported browser transports retain deliberate system browser confirmation without wallet access. Custom URLs and Recent keep their confirmation path, and signing stays in separate wallets screens.

The browser shows the dApp icon/title, the actual origin, navigation and a network indicator/menu. About in the menu reveals details and origin-only sharing. Developer site, terms, privacy and support are optional public HTTPS text; supported networks are derived from validated advertised URLs. None of these fields changes the launch URL, origin or connection decision. Existing account/network retirement behavior remains unchanged; changing networks closes the current browser.
